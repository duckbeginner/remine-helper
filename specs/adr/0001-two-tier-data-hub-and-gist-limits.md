# ADR-0001: 2계층 데이터 허브 아키텍처 및 Gist 1MB 제한 제약

- **상태 (Status)**: `ACCEPTED`
- **결정 일자**: 2026-08-25
- **결정자 (Deciders)**: 프로젝트 아키텍트 (@duckbeginner) & AI 페어 프로그래머
- **영향 범위**: `scripts/data-hub/`, `docs/api/v1/`, GitHub Gist 배포 파이프라인

---

## 1. 컨텍스트 및 문제 정의 (Context)
- Remine Helper는 클라이언트 확장 프로그램 및 웹 사이트에 실시간 데이터를 서빙하기 위해 GitHub Gist를 무비용/초고속 분산 CDN으로 활용합니다.
- 그러나 GitHub Gist는 단일 파일의 크기가 **1MB를 초과하면 내용이 Truncate(잘림)**되는 치명적인 플랫폼 제약이 존재합니다.
- RESCENE의 일정, 영상, SNS 데이터가 지속적으로 누적됨에 따라 단일 `data.json` 파일 모델은 1MB를 초과하여 클라이언트 파싱 에러 및 전체 서비스 마비를 야기할 위험이 임박했습니다.

---

## 2. 고려된 대안들 (Alternatives Considered)
1. **대안 A: 외부 유료 BaaS/클라우드 DB 도입 (Firebase Firestore, Supabase 등)**
   - *장점*: 1MB 파일 크기 제약 없이 유연한 쿼리 가능.
   - *기각 사유*: API Key 노출 위험, 월간 무료 트래픽 초과 시 과금 발생, 브라우저 확장 프로그램의 오프라인 캐시 및 단순성 저해.
2. **대안 B: 단순 파일 분할 (월별/연도별 디렉터리 API 분할)**
   - *장점*: 파일 크기를 영구적으로 작게 유지 가능.
   - *기각 사유*: 클라이언트가 전체 일정을 검색하거나 캘린더 월간 이동 시 매번 수십 번의 네트워크 요청을 병렬 전송해야 하므로 로딩 지연 및 GitHub API 레이트 리밋 발생.
3. **대안 C (선택): 2계층(2-Tier) 분리 모델 (`core.json` + `schedules.json`)**
   - *장점*: 15분 주기 백그라운드 폴링은 초경량 `core.json`으로 초고속 서빙하고, 무거운 전체 아카이브는 필요할 때만 1회 Lazy-loading하여 비용 0원과 최고 성능을 양립.

---

## 3. 최종 결정 사항 및 핵심 규칙 (Decision & Rules)
1. **Tier 1 (`core.json`) - 초경량 헤드 데이터**:
   - 최근 7일 영상, 공식 공지, 당월/익월 핵심 일정만 포함.
   - **엄격한 크기 제한: 최대 160KB 이하 유지**.
   - 클라이언트 백그라운드 워커가 15분 주기로 경량 폴링.
2. **Tier 2 (`schedules.json`) - 마스터 일정 아카이브**:
   - 2024년 데뷔 이후의 전체 일정 수록.
   - **엄격한 크기 제한: 최대 600KB 이하 유지** (1MB Gist truncate 마진 400KB 확보).
   - 대시보드 캘린더 전체 조회 시에만 Lazy-loading.
3. **Ops 전수 검수 아카이브 (`master-schedules.json`)**:
   - 숨김/필터링된 일정까지 포함하는 전수 데이터로, 최대 800KB 이내로 관리.

---

## 4. 기대 효과 및 불변 제약 (Consequences & Invariants)
- **기대 효과**:
  - Gist 1MB 파일 잘림 위험을 원천 박멸.
  - 클라이언트 백그라운드 네트워크 트래픽 80% 이상 절감.
- **불변 제약 (Invariants)**:
  - CI 파이프라인의 `validate.js`는 `core.json`이 160KB를 초과하거나 `schedules.json`이 600KB를 초과할 경우 배포를 즉각 중단(Exit 1)한다.
  - 마스터 아카이브 용량 절감을 위해 사용하지 않는 레거시 필드(`extField`, YouTube 중복 썸네일 URL)는 배포본에서 영구 배제한다.
